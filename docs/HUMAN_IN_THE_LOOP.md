# Human-in-the-Loop 기록

> AI가 제안하거나 수행한 일에 **사람이 어디서, 왜 개입했는지**를 시간순으로 기록합니다.
> 표기: 🧑 사람의 결정 · 🤖 AI의 제안/수행 · ✅ 채택 · ✏️ 수정 후 채택 · ❌ 거부

---

## #1 주제 선정: "운 타임머신"

| 구분 | 내용 |
|---|---|
| 🤖 AI | 과제 조건(하루 완성, 무료 API, AI 다양한 활용)에 맞춰 아이디어의 적합성을 평가하고, 단계별 AI 활용 방안을 제안 |
| 🧑 사람 | 과거에 구상했던 "후행지표로 보는 운" 아이디어를 제시. 범위는 **주식은 보류하고 로또부터** 하기로 결정 |
| 결과 | ✏️ 수정 후 채택. AI는 로또+비트코인을 제안했지만 사람이 범위를 더 좁힘 |
| 이유 | 하루라는 제약 안에서 데이터 하나를 제대로 검증하는 것이 여러 데이터를 얕게 다루는 것보다 낫다고 판단 |

## #2 데이터 원칙: "AI가 말한 숫자는 믿지 않는다"

| 구분 | 내용 |
|---|---|
| 배경 | 1년 전 AI에게 로또 번호를 요청했을 때 **무작위 번호를 실제 당첨번호라고 답한 경험** |
| 🧑 사람 | "사실관계 파악이 가장 중요하다. 정제는 그 다음"이라고 작업 순서를 지정 |
| 🤖 AI | 기억에서 번호를 꺼내지 않고, 공식 사이트에서 직접 수집한 뒤 **내부 정합성 검사와 외부 언론 대조**의 2단계 검증을 설계·수행 |
| 결과 | ✅ 1,244개 회차 수집, 정합성 실패 0건, 표본 7개 회차 외부 대조 전부 일치 → [검증 보고서](DATA_VERIFICATION.md) |
| 이유 | 이 서비스의 가치는 "실제 과거 기록"에 있으므로, 데이터의 진위가 서비스의 존재 이유와 같다 |

### 이 과정에서 드러난 AI의 한계와 대응

| 상황 | 사람의 대응 원칙 |
|---|---|
| 널리 알려진 공식 API가 이미 작동하지 않았음. AI의 학습 지식이 낡았을 수 있음 | AI가 "알고 있는" 방법도 실제로 호출해 보고 결과로 판단 |
| 정합성 검사는 가짜 번호도 통과할 수 있음 | "검사 통과 = 진짜"로 보지 않고, 독립 출처 대조를 별도로 요구 |
| 제3자 집계 사이트에도 오류가 있었음(1100회 목록 행) | 제3자 데이터는 원천이 아닌 대조용으로만 사용 |

## #3 정제 기준: "모르면 비운다"

| 구분 | 내용 |
|---|---|
| 🧑 사람 | 번호, **연도까지 정확한 날짜**, 금액을 모두 정제하도록 요구. "1인당 당첨금을 알 수 없으면 **비워둬도 된다**"고 허용 |
| 🤖 AI | 필드 설명이 없는 원본 금액 필드의 의미를 가설로 세우고 데이터와 언론 보도로 검증. 정제 결과를 원본과 다시 대조해 다르면 실패하도록 설계 |
| 결과 | ✅ 1,244개 회차 정제, 원본 대조 실패 0건 → [검증 보고서 6장](DATA_VERIFICATION.md#6-정제) |
| 이유 | "0원"과 "모름"이 섞이면 서비스가 사실과 다른 결과를 보여줄 수 있음. 빈칸이 거짓보다 낫다 |

### 자동 검사가 잡은 이상치: 381회

| 구분 | 내용 |
|---|---|
| 🤖 AI | 정제 스크립트가 381회 1·2등의 `인원 × 1인당 ≠ 총액`을 발견하고 **파일 생성을 중단** |
| 판단 기준 | 어느 값을 믿을지 AI가 임의로 고르지 않고, 2010년 당시 기사를 찾아 대조 |
| 결과 | ✏️ 기사와 일치하는 **1인당 금액은 유지, 총액만 비움.** 예외는 스크립트에 근거와 함께 명시해 다른 불일치는 계속 걸러지게 함 |

### AI가 확인하지 못해 제외한 것

| 항목 | 제외 이유 |
|---|---|
| 1등 0명 회차의 이월금 | 원본 값이 이월금으로 보이지만 외부 근거를 찾지 못함 (→ #4에서 확인 후 추가) |
| 회차 판매액 | 비슷한 필드 두 개의 차이를 확인하지 못함 |

## #4 계산 모델 전환: "검색하는 사람이 당첨자 한 명을 더한다"

| 구분 | 내용 |
|---|---|
| 🤖 AI | 당첨자 0명인 등수의 1인당 금액을 "존재하지 않는 값"으로 보고 비움. 실제 1인당 금액을 그대로 보여주는 것을 전제로 정제 |
| 🧑 사람 | **"당첨자가 0명이면 그때 내가 그 번호였다면 그 금액을 받는 거 아냐? 검색하는 사람은 당첨자가 한 명 더 추가되는 거니까 금액이 새로 계산되어야 한다"**고 지적 |
| 🤖 AI | 등수별 배분 구조를 데이터와 기사로 확인. 1~3등은 나눠 갖고 4·5등은 고정이며, 1등 0명 회차의 원본 값이 실제 이월금임을 확인. 이를 바탕으로 계산 규칙을 제안 |
| 🧑 사람 | 규칙을 승인하면서 범위를 정함: **288회 이전 데이터 제외**(정확하지 않음), **1장 구매만**, **이월 연쇄 효과 무시**. "정확성이 중요하니 확장성은 지금 고려하지 않는다" |
| 결과 | ✏️ 수정 후 채택 → [검증 보고서 7장](DATA_VERIFICATION.md#7-가상-당첨금-계산-규칙). 가상 금액은 사실이 아니므로 데이터에 저장하지 않고 화면에서만 계산 |
| 의미 | AI는 데이터를 "사실 기록"으로만 보고 있었고, 사람이 **서비스 사용자의 관점**에서 숫자의 의미를 다시 정의함 |

### 규칙을 적용하다 드러난 AI의 오류

| 상황 | 대응 |
|---|---|
| AI가 "등수 총액은 289회부터 기록된다"고 보고했지만, 실제로는 289회 다음 290~293회가 비어 있었음 | 정제 스크립트의 검사가 실패하며 드러남. 사람이 정한 원칙("총액 기록이 없는 구간은 쓰지 않는다")을 일관되게 적용해 **294회부터**로 조정 |
| 교훈 | AI의 데이터 요약도 검증 대상. 사람이 정한 원칙을 코드 검사로 만들어 두면 AI의 착오를 자동으로 잡을 수 있음 |

## #5 비용 구조 확인과 기술 선택

| 구분 | 내용 |
|---|---|
| 🧑 사람 | "화면마다 계산한다"는 설명을 듣고 **계산할 때마다 비용이 드는 구조가 아닌지** 확인을 요구 |
| 🤖 AI | 계산은 사용자 브라우저에서 실행되며, 완성된 서비스에는 API·AI 호출이 없고 정적 호스팅으로 무료 배포가 가능함을 설명 |
| 🧑 사람 | AI가 추천한 React+Vite를 그대로 받지 않고 **"왜 이걸로 하는지는 내가 알아야 한다"며 근거와 대안을 요구** |
| 🤖 AI | React, Vue, Svelte, 바닐라 JS, Next.js를 과제 기준(컴포넌트 문서, 하루 일정, 정적 배포, 본인이 설명 가능한지)으로 비교. 추천 이유 중 "AI가 다루기 편하다"는 AI 쪽 사정도 숨기지 않고 밝힘 |
| 🧑 사람 | **React로 결정** |
| 결과 | ✅ 채택. 컴포넌트 문서와 코드 구조를 일치시킬 수 있고, 포트폴리오 활용도가 높음 |
| 의미 | 도구 선택을 AI에게 위임하지 않고, 판단 근거를 이해한 뒤 사람이 결정 |

## #6 화면 기획: 사람이 직접 설계

| 구분 | 내용 |
|---|---|
| 배경 | 사람이 "화면 구성을 기획할 때는 나를 다시 찾아달라"고 요청. AI는 데이터·계산 준비까지만 하고 멈춘 뒤, 입력·결과·톤 세 가지 질문을 정리해 넘김 |
| 🧑 사람 | **입력:** 동그라미 6칸을 눌러 번호 선택(키보드 입력 없음) · **결과:** 총 당첨 횟수와 금액을 크게, 아래에 회차별 리스트 · **톤:** 유머러스하게 · **구성:** 랜딩 없이 이 서비스 하나만 · **연출:** 버튼을 누르면 화면 중앙에 공 뽑기 기계 애니메이션, 결과는 이펙트와 소리로 과장되게 |
| 🤖 AI | 기획을 컴포넌트로 옮겨 구현. 세부 연출(돔 안에서 공이 뒤섞임, 회차 번호가 굴러가는 문구, 등수별 폭죽 양과 화면 흔들림 세기, 낙첨 시 먹구름 비와 슬픈 트롬본)과 유머 문구를 제안·작성 |
| 결과 | ✅ 기획대로 구현 → [UI 컴포넌트 문서](UI_COMPONENTS.md) |

### AI가 덧붙인 것 (사람의 검토 필요)

| 추가 요소 | 이유 |
|---|---|
| 🎲 "아무거나 골라줘" 버튼 | 번호를 고르기 귀찮은 사용자를 위해 |
| 번호를 고르면 다음 빈칸으로 자동 이동 | 6번 반복해서 칸을 누르는 수고를 줄이기 위해 |
| 회차별 기록에 계산 근거 한 줄 | 실제 당첨금과 금액이 다른 이유를 바로 알 수 있게 |
| 손해일 때 "치킨 약 N마리" 환산 | 유머 톤 강화. 치킨 한 마리 2만 원으로 가정 |
| 소리 끄기 버튼 | 공공장소에서 갑자기 소리가 나는 것을 막기 위해 |

### 구현 중 AI가 실제 화면으로 확인하고 고친 것

| 발견 | 수정 |
|---|---|
| 뽑기 기계 안의 공이 보이지 않음 (CSS 계산식 오류) | 공 위치를 고정 좌표로 변경 |
| 휴대폰 폭에서 번호 6칸이 두 줄로 넘어가고, 번호판 오른쪽 열이 잘림 | 공 크기를 화면 폭에 맞춰 줄어들게 변경 |
| 화면이 흔들릴 때 가로 스크롤바가 생김 | 가로 넘침 숨김 |
| 번호를 다 골라도 기계 문구가 "번호 6개를 골라주세요"로 남음 | "준비 완료! 돌려볼까요?"로 바뀌게 수정 |
| 개발 서버가 수정된 파일을 감지하지 못하고 예전 화면을 보여줌 | 서버가 실제로 보내는 파일 내용을 직접 확인해 원인을 찾고 재시작 |

## #7 화면 다듬기와 배포

| 구분 | 내용 |
|---|---|
| 🧑 사람 | 소리·유머 문구·넓은 화면을 직접 확인하고 승인. **"문장이 마침표나 쉼표로 이어질 때 줄바꿈"**을 요청 |
| 🤖 AI | 쉼표 뒤에 공백이 올 때만 줄을 바꾸도록 구현. 숫자 안의 쉼표(`1,000원`)는 줄바꿈하지 않게 함 |
| 🧑 사람 | 배포 방식으로 GitHub를 선택. **"이후 프로젝트에서도 계속 쓸 것"**이라며 일회성 업로드가 아닌 GitHub 연동을 요구 |
| 🤖 AI | GitHub Pages와 Netlify·Vercel을 비교해 "코드·문서·서비스 주소가 한곳에 모인다"는 이유로 GitHub Pages 추천. 공식 GitHub 플러그인을 찾아 안내하고, 플러그인이 현재 대화에는 불러와지지 않은 것을 확인한 뒤 git으로 진행하는 방법 제시 |
| 판단 지점 | 공개 저장소에 올리기 전에 **커밋 기록에 이메일이 공개된다**는 점을 AI가 알리고 확인을 요청 |
| 🧑 사람 | 개인 이메일 대신 GitHub의 noreply 주소를 쓰기로 결정 |
| 결과 | ✅ 코드를 올리면 GitHub Actions가 **테스트를 통과해야만** 빌드·배포하도록 구성 |

### 배포 실패와 해결

| 순서 | 내용 |
|---|---|
| 1차 실패 | 테스트·빌드는 통과했지만 배포 단계에서 실패. AI가 로그인 없이 조회한 정보만 보고 **"Pages가 꺼져 있다"고 잘못 진단** |
| 🧑 사람 | 설정 화면을 캡처해 **"이미 설정되어 있다"고 반박** |
| 🤖 AI | 진단을 다시 하고, 배포 기록의 오류 메시지를 직접 찾아 진짜 원인을 확인: 배포 환경(`github-pages`)이 허용하는 브랜치 목록에 `main`이 없음 |
| 🧑 사람 | 설정을 고치면서 **저장소 기본 브랜치가 `master`로 되어 있던 것이 원인**임을 발견 |
| 해결 | 배포 성공. 배포 도구를 최신 버전으로 올려 경고도 정리. AI가 실제 배포 주소에서 번호 선택부터 결과까지 동작을 확인 |
| 교훈 | AI의 진단도 검증 대상. 사람이 실제 화면을 근거로 반박해 잘못된 방향으로 가는 것을 막음 |
