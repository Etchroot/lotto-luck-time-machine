# AI 활용 목적 기록

> 각 단계에서 **AI에게 어떤 역할을 맡겼는지, 왜 AI를 썼는지, 무엇은 AI에게 맡기지 않았는지**를 기록합니다.
> AI가 낸 결과를 사람이 어떻게 판단했는지는 [Human-in-the-Loop 기록](HUMAN_IN_THE_LOOP.md)에 따로 정리했습니다.

## 한눈에 보기

| 단계 | AI의 역할 | 활용 목적 | AI에게 맡기지 않은 것 |
|---|---|---|---|
| 1. 기획 | 기획 검토자 | 아이디어가 과제 조건에 맞는지 객관적으로 평가 | 주제와 범위 결정 |
| 2. 데이터 수집 | 조사원 + 리버스 엔지니어 | 공식 데이터 경로를 찾고 수집 자동화 | **데이터 자체 (AI의 기억 속 번호는 사용 금지)** |
| 3. 데이터 검증 | 팩트체커 + 감사관 | 수집 데이터의 진위를 독립 출처로 확인 | "검증 통과"의 최종 판단 기준 |
| 4. 데이터 정제 | 데이터 분석가 | 설명 없는 필드의 의미를 가설과 검증으로 밝힘 | "모르면 비운다"는 원칙 |
| 5. 계산 모델 | 도메인 리서처 + 개발자 | 로또 배분 구조를 조사해 계산 규칙으로 구현 | 계산 모델의 관점("나도 당첨자 한 명")과 범위 |
| 6. 기술 선택 | 기술 자문 | 선택지를 과제 기준으로 비교 | 최종 선택 |
| 7. 기록 | 서기 | 작업과 동시에 판단 과정을 문서로 남김 | 기록 내용의 사실 확인 |
| 8. 화면 구현 | 프론트엔드 개발자 + 모션 디자이너 | 사람의 기획을 컴포넌트와 애니메이션으로 구현 | 화면 기획(입력 방식, 결과 구성, 톤, 연출 방향) |
| 9. 효과음 | 사운드 디자이너 | 음원 파일 없이 소리를 코드로 합성 | 소리를 넣을지, 어떤 분위기일지 |
| 10. 문구 | 카피라이터 | 등수·손익별 유머 문구 작성 | 유머 톤으로 간다는 결정, 최종 문구 검토 |
| 11. 화면 검증 | QA 테스터 | 브라우저에서 실제로 클릭하며 화면 확인 | 완성도 최종 판단 |

---

## 1. 기획: 기획 검토자로서의 AI

- **무엇을 맡겼나:** "과거 데이터로 보는 운" 아이디어가 과제 조건(하루 완성, 무료 API, AI를 다양하게 활용)에 맞는지 평가하고, 위험 요소와 AI 활용 지점을 제안하게 함
- **왜 AI인가:** 혼자 떠올린 아이디어는 장점만 보이기 쉬움. 조건표에 대고 냉정하게 점검해 줄 상대가 필요했음
- **얻은 것:** "AI가 숫자를 계산하면 안 된다", "투자 조언처럼 보이면 안 된다" 같은 위험 요소를 초기에 파악

## 2. 데이터 수집: 조사원이자 리버스 엔지니어로서의 AI

- **무엇을 맡겼나:** 공식 로또 데이터를 얻을 경로를 찾고 수집 스크립트를 작성
- **왜 AI인가:** 널리 알려진 공식 API가 이미 작동하지 않았음. AI가 공식 사이트의 HTML과 JavaScript를 직접 분석해 **페이지가 내부적으로 쓰는 데이터 경로를 찾아냄.** 사람이 혼자 했다면 개발자 도구를 오래 뒤져야 했을 작업
- **맡기지 않은 것:** 번호 데이터 자체. 과거에 AI가 무작위 번호를 실제 번호라고 답한 경험이 있어, **AI의 기억에서 나온 숫자는 한 개도 쓰지 않기로** 함
- **결과물:** [`scripts/collect-lotto.mjs`](../scripts/collect-lotto.mjs), 원본 [`data/raw/lotto-dhlottery.json`](../data/raw/lotto-dhlottery.json)

## 3. 데이터 검증: 팩트체커이자 감사관으로서의 AI

- **무엇을 맡겼나:** 수집한 1,244개 회차가 진짜인지 확인
- **왜 AI인가:** 검증을 두 층으로 설계하고 실행하는 데 활용
  - **감사관 역할:** 회차 연속성, 번호 범위·중복, 추첨일 요일 같은 정합성 검사 코드 작성 ([`scripts/verify-lotto.mjs`](../scripts/verify-lotto.mjs))
  - **팩트체커 역할:** 정합성 검사는 가짜 번호도 통과할 수 있으므로, 언론 기사를 웹에서 찾아 표본 회차를 대조
- **얻은 것:** 제3자 집계 사이트의 오류(1100회)까지 발견해 "공식 출처만 원천으로 쓴다"는 원칙의 근거가 됨
- **결과물:** [데이터 검증 보고서](DATA_VERIFICATION.md)

## 4. 데이터 정제: 데이터 분석가로서의 AI

- **무엇을 맡겼나:** 설명이 없는 원본 필드(1인당 금액인지 총액인지 등)의 의미 파악과 정제
- **왜 AI인가:** 필드 의미를 추측하지 않고 **가설을 세운 뒤 전 회차 데이터와 언론 보도로 검증**하는 분석가 방식으로 일하게 함
- **얻은 것:** 자동 검사가 381회의 이상치를 잡았고, AI가 2010년 기사를 찾아 어느 값이 맞는지 판별함
- **결과물:** [`scripts/refine-lotto.mjs`](../scripts/refine-lotto.mjs), [`data/lotto.json`](../data/lotto.json)

## 5. 계산 모델: 도메인 리서처이자 개발자로서의 AI

- **무엇을 맡겼나:** "내가 한 명 더 당첨됐다면"의 금액 계산 규칙 조사와 구현
- **왜 AI인가:** 로또의 등수별 배분 구조(나눠 갖는 등수와 고정 금액 등수, 이월 규칙)를 데이터 패턴과 기사로 확인하는 리서치에 활용. 확인한 규칙을 코드와 테스트로 옮김
- **맡기지 않은 것:** 계산 모델의 관점. "검색하는 사람이 당첨자 한 명을 더한다"는 핵심 아이디어는 사람이 냄
- **결과물:** [`src/lib/prize.js`](../src/lib/prize.js), 테스트 [`src/lib/prize.test.js`](../src/lib/prize.test.js) (8개 통과)

## 6. 기술 선택: 기술 자문으로서의 AI

- **무엇을 맡겼나:** 프론트엔드 기술 선택지 비교
- **왜 AI인가:** 여러 프레임워크의 장단점을 과제 기준에 맞춰 빠르게 비교하는 데 활용
- **맡기지 않은 것:** 최종 선택. 사람이 추천 근거를 직접 요구해 이해한 뒤 React로 결정

## 7. 기록: 서기로서의 AI

- **무엇을 맡겼나:** 작업과 동시에 이 문서, Human-in-the-Loop 기록, 검증 보고서를 작성
- **왜 AI인가:** 작업이 끝난 뒤에 쓰면 기억에 의존하게 되고, 판단의 이유가 빠짐. 작업하는 순간의 근거를 바로 남기기 위해 활용
- **맡기지 않은 것:** 내용의 사실 확인. 기록된 판단이 실제 대화와 맞는지는 사람이 검토

## 8. 화면 구현: 프론트엔드 개발자이자 모션 디자이너로서의 AI

- **무엇을 맡겼나:** 사람이 정한 화면 기획(동그라미 번호 선택, 결과 요약 + 회차 리스트, 뽑기 기계 연출)을 React 컴포넌트로 구현
- **왜 AI인가:** 기획 의도를 애니메이션 세부(공이 뒤섞이는 움직임, 결과 공이 튀어나오는 탄성, 등수별 화면 흔들림 세기)로 구체화하는 데 활용
- **맡기지 않은 것:** 화면 기획 자체. 사람이 "화면 기획 때는 나를 다시 불러달라"고 요청했고, AI는 그 전 단계에서 멈춤
- **결과물:** [UI 컴포넌트 문서](UI_COMPONENTS.md), [`src/components/`](../src/components/)

## 9. 효과음: 사운드 디자이너로서의 AI

- **무엇을 맡겼나:** 추첨 중 소리, 등수별 팡파르, 낙첨 시 슬픈 트롬본
- **왜 AI인가:** 무료 음원을 찾아 라이선스를 확인하는 대신, **Web Audio API로 소리를 직접 합성**함. 음원 파일이 없어 비용과 저작권 문제가 없고, 등수에 따라 팡파르 길이를 코드로 조절할 수 있음
- **결과물:** [`src/lib/sound.js`](../src/lib/sound.js)

## 10. 문구: 카피라이터로서의 AI

- **무엇을 맡겼나:** 등수별 제목("전생에 나라를 구하셨군요"), 손익별 한마디("그 돈이면 치킨을 먹었어야 했습니다")
- **왜 AI인가:** 같은 톤의 문구를 여러 개 만들어 결과마다 다르게 보여주기 위해
- **지킨 원칙:** 문구에 숫자를 직접 쓰지 않음. 숫자는 항상 계산 결과에서 채워, 문구 때문에 사실과 다른 숫자가 나오지 않게 함
- **결과물:** [`src/content/copy.js`](../src/content/copy.js)

## 11. 화면 검증: QA 테스터로서의 AI

- **무엇을 맡겼나:** 내장 브라우저에서 휴대폰 폭으로 실제 클릭하며 번호 선택 → 추첨 → 결과까지 확인
- **왜 AI인가:** 코드만 보고 "될 것"이라고 넘기지 않고, 실제 화면에서 확인하기 위해. 1000회 당첨번호로 테스트해 1등이 나오는지, 총액이 계산과 맞는지(1등 1,192,610,071원 + 5등 21회 × 5,000원 = 1,192,715,071원) 대조
- **얻은 것:** 코드 리뷰로는 놓쳤을 문제 4건(공이 안 보임, 휴대폰에서 줄바꿈, 가로 스크롤, 문구 미변경)을 발견해 수정
- **자동 테스트:** 계산·집계 로직 테스트 11개 통과 (`npm test`)
